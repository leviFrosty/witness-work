# WitnessWork bottom navigation and header proposal

September 30, 2026 · Code reviewed at `f203bff7` · Recommendation for validation, not an implementation.

**Recommend a maximum of four bottom destinations: Home → Schedule → Contacts → Progress, with a separate, labeled Add action.** Put Map inside Contacts as a visible, remembered List / Map view. Put Buddies beside the Schedule title, with its actionable request badge. Give every root screen the same header structure: avatar, section title, section-specific action.

This preserves the main jobs—start today's work, plan future work, revisit Contacts, review recorded service—while making room for labels and future features. The highest-risk change is moving Map. Treat it as a hypothesis to test with existing Map users, not an obvious deletion justified by lower traffic.

## What the current app does

The phone bar is currently `Home · Contacts · Progress · Schedule · [Buddies] · Map`, followed by a separate plus button. Progress follows the hours capability; Buddies requires its feature flag and native module. Without hours logging the bar loses Progress; with hours and Buddies it reaches six destinations plus Add. Developer Tools can add another destination, but that is not a normal user case. Wide layouts add Settings in a sidebar. [Navigator](../../src/app/navigation/HomeTabStack.tsx), [Publisher capabilities](../../src/lib/publisherCapabilities.ts), [Buddies availability](../../src/features/buddies/hooks/useBuddiesEnabled.ts).

The floating bar already uses a contemporary visual treatment. Its information hierarchy is the more useful design target: a 52-point capsule, 18-point phone icons, and a text label only on the selected destination. Labels can shrink to 70% of their original size. Consequently, users need to recognize inactive icons, and adding a feature competes for the same narrow space. [Tab bar](../../src/components/ui/TabBar.tsx).

| Current surface | Header / top of screen                                                                                            | Design implication                                                                       |
| --------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Home            | Settings hamburger, no visible central title, notifications bell, optional Support heart; Profile card in content | Global controls are concentrated on Home and compete with identity content.              |
| Contacts        | Large title inside a card, overflow, Add Contact, search and filters                                              | Strong local tools, but a second plus coexists with global Add.                          |
| Schedule        | Month navigation, insights, calendar controls, Create Plan                                                        | The date describes the content; it does not consistently name the section.               |
| Progress        | Month / Year / All-time, then date controls                                                                       | Local hierarchy is useful but lacks the same root header structure.                      |
| Map             | Dedicated geographic workspace and map controls                                                                   | It is a Contacts representation, but some users also approach it as an independent task. |

The global Add sheet currently offers Add Time when the capability allows it, Create Plan, and Add Contact. It has no dedicated open/selection attribution events. The success event's `source: time_entry_form` identifies the form, not whether a person reached it from global Add or another button. [Quick actions](../../src/components/QuickActionMenu.tsx), [time-entry instrumentation](../../src/features/service-reports/screens/AddTimeScreen.tsx).

### Findings that affect the layout

- **Time entry deserves immediate access.** The week contains 14,649 `time_entry_created` events from 3,335 IDs. The Add Time screen reaches 83.7% of the observed population. Preserve a direct Home action and logging from a selected Schedule day. These separate counts are not a completion funnel.
- **Schedule is a major destination even when someone is not creating Plans.** It reaches 2,656 IDs, while `plan_created` comes from 328 IDs. The screen also supports calendar browsing and logging. Naming the tab “Plan” or making it only a creation surface would underdescribe its job.
- **Contacts and Map overlap, but not completely.** Of 1,527 Map sessions, 954 also contain a Contacts screen event; 573—**37.5%**—do not. Consolidation has a credible semantic basis and a real access-cost risk. Same-session co-occurrence does not establish the order of those visits.
- **Map has a smaller recurring audience worth protecting.** Of 906 Map IDs, 228 used it on at least two distinct days and 40 in at least five sessions that week. `map_contact_selected` came from 126 IDs and fired 1,235 times. That shows concentrated interaction; absence of this event does not mean a map view had no value.
- **Progress has enough observed reach to keep its own home.** Its 37.0% population reach is especially unpersuasive as an argument for removal because eligibility is unmeasured. Keep Home's summary compact and longer history in Progress.
- **A permanent Home Support heart is less strongly justified than the main tasks.** In the wider observed window it opened the paywall for 28 IDs, compared with 36 from Settings. Move Support to a visible row near the top of the avatar menu as a design hypothesis. These are opening counts, not purchase attribution; protect completed support flows when testing.

Sources: `actions7`, `cooccurrence7`, `map-frequency7`, `paywall-sources`, and `previous-screen7` in the bundle. Small denominator differences between SQL session grouping and the typed session aggregation are retained in the evidence; headline denominators consistently use the typed query. Snapshot timing and session handling can produce small differences. Map subgroup counts agree across these queries.

### Limits that change the recommendation

1. **Reach is measurable; complete navigation sequences are not.** Current code sends each screen once per PostHog session. Older or differently deployed builds in the sample still produce repeated screen events. The deduplication policy makes raw view totals and apparent paths unsuitable for measuring backtracking, repeated tab taps, or time to find a task. I inspected the paths query as supporting context only. `previous_screen` is attribution on an emitted screen event, not a record of every transition. [Analytics contract](../../docs/analytics.md), [adapter](../../src/lib/analytics.ts).
2. **Buddies is unmeasured here.** No Buddies screen appears in the returned production results, its custom events are absent from the discovered event inventory, and the project lookup finds no nondeleted feature flag matching `buddies`. Current code nevertheless contains a gated Buddies tab. This is an exposure/rollout gap, not evidence of low demand. The Schedule placement comes from Buddies' shared-planning purpose, not adoption numbers.
3. **The reporting cycle is incomplete.** The sample misses the beginning of the month; 28 reporting-export IDs in the week cannot establish the importance of monthly reporting. Different export methods also have different outcome semantics. Keep the report easy to find.
4. **Android evidence is thin.** The week contains 13 Android IDs, alongside 3,899 iOS and 134 iPadOS IDs. These breakdowns can overlap. Do not claim platform parity from that sample; test Android separately.
5. **Instrumentation leaves specific holes.** There are no dedicated tab-selection or global Add events. `notifications_tray_opened` exists in taxonomy but returned zero in this production window. Neither absence supports removing that UI. Settings is a Home drawer on compact screens, so the rare `Settings` route is not a count of all settings access.
6. **Identity and consent affect counts.** Analytics is anonymous, optional, and can reset identifiers during consent changes and migration. No claim about unique people, all installations, or identifiable Publisher-role cohorts follows from these data. The role/capability fields needed for eligible-use comparisons are not available on the discovered screen events.

## Proposed layout

```text
ROOT HEADER       [Avatar]   Section title            [Local action]
LOCAL CONTROLS               Views / date / scoped search
CONTENT                     Current task and primary action
WHEN RUNNING                Compact timer status + return control
BOTTOM            Home     Schedule     Contacts     Progress    [＋ Add]
```

The four destinations are the hours-enabled layout. Preserve the existing capability variant: without hours logging, show **Home · Schedule · Contacts**, keep participation and the Service Report on Home, and omit time/timer actions. Do not insert, reorder, or replace a bottom tab when the Buddies flag changes. Capability changes should be deliberate and explained; navigation should not reshuffle according to daily usage.

| Destination  | Main job                                              | Header action / local controls                                                                          | Content boundary                                                                                                                                                                            |
| ------------ | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Home**     | Start today's service and check current status        | Avatar → Profile and Settings; bell → notifications                                                     | Direct Add Time or participation action, compact Service Report with View Report, upcoming work. Detailed historical analysis remains in Progress.                                          |
| **Schedule** | See and arrange future work; work with a selected day | Labeled **Buddies** entry and actionable badge when available. Date/calendar controls below the title.  | Plans, relevant Follow-ups, shared planned days, and direct logging from the selected day. Buddies roster, pairing, requests, and privacy controls remain coherent inside their own screen. |
| **Contacts** | Find a Contact and prepare or record a Visit          | Filter/overflow action. Visible **List / Map** selector and Contacts search below the title.            | The existing list and map workspaces. Preserve view, filter, search, map camera, and selected Contact when moving around. Contact Details retains its direct Visit action.                  |
| **Progress** | Review recorded service and history                   | **Report** opens Service Report with an explicit period. Month / Year / All-time stays below the title. | Historical entries, monthly totals, Service Year, and applicable goals/milestones. Do not make past-time review compete with future planning in one crowded calendar.                       |

**Avatar and header:** use one consistent account/settings entry on root screens. Its first-level menu contains Profile, Settings, Support WitnessWork, and Help Center; retain existing import/backup navigation. A small number of meaningful contextual controls remains on the trailing side. Home keeps the bell; badges on Schedule can expose actionable Buddies requests elsewhere. Use titles that name the section, and date/range controls that describe its contents. Prefer concise labels over explanatory text or another permanent toolbar.

**Map migration:** List / Map must be visible, not in overflow. Default to List for new users; remember the explicitly selected view for returning users. Preserve Map deep links and map-to-contact paths, and carry a clearly chosen migration default for known Map-first users if that preference can be determined locally without guessing. Visiting Contacts from another section should restore its last workspace. First-time discovery and switching from List to Map still cost an extra tap; remembering state does not eliminate that tradeoff. A direct Map shortcut can remain in a relevant Home/field workflow if research shows the need.

**Buddies migration:** keep its name and concepts intact. It shares future Plans, so Schedule is the appropriate parent. Do not mix buddies into Contacts: the latter are people visited in ministry. Preserve invite deep links, native/rollout availability, requests, and routes from notifications. Promote it back to a bottom destination only if eligible usage and task research establish a substantial independent job. [Domain definitions](../../CONTEXT.md).

**Add:** retain the existing global action for the first iteration and label it Add. Its meaning and menu ordering stay stable across roots: Add Time when allowed, Create Plan, Add Contact. A contextual Visit action belongs on Contact Details. Keep direct Home/day logging so the most common action does not require opening this menu. Measure use before removing or radically changing the global action. The plus must never appear selected like a destination.

**Ongoing timer:** only while running, consider a compact status accessory above the bar that returns to timer controls. This is a way to preserve an ongoing task across sections; do not allocate a permanent Timer tab or add a permanently empty accessory. Respect the existing hours capability.

**Navigation behavior:** preserve each destination's stack, scroll, search, and selected date/view. A root reselect can scroll to the top; a detail reselect can return to that destination's root, provided it cannot discard a draft. Ordinary detail pages should retain a clear parent and predictable Back behavior; focused forms can cover navigation and return to their origin after Save. On Android, verify hardware/system Back as well as visible Back. Do not add a Cancel button to an already dismissible form sheet.

**Platform and accessibility:** keep the same destination order and semantics on iOS and Android, with platform-appropriate bar material and behavior. iOS can retain the floating treatment; Android must remain legible without Liquid Glass. Keep labels visible, provide a clear selected state and accessible names, use at least 44-point iOS / 48-dp Android controls, and accommodate larger text and long translations without shrinking away meaning. On wider windows, project the same destinations into a rail/sidebar and retain secondary Settings there. Touch-target references: [Apple buttons](https://developer.apple.com/design/human-interface-guidelines/buttons), [Android accessibility](https://developer.android.com/design/ui/mobile/guides/foundations/accessibility). The concept is a hierarchy sketch, not a measured native layout or a translation test.

## Alternatives and confidence

| Candidate                                                    | Benefit                                      | Cost / decision                                                                                                                            |
| ------------------------------------------------------------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Keep five or six destinations and restyle the bar            | Minimal migration                            | Does not solve competing destinations or label pressure. Adding Buddies still changes the bar.                                             |
| **Four roots; Map within Contacts; Buddies within Schedule** | Clear jobs, room for labels, coherent growth | **Recommended to prototype.** Medium confidence in the grouping; Map access must survive validation.                                       |
| Three roots; move Progress inside Home                       | More space                                   | Adds access cost to a distinct task used by 37% of observed IDs, with an unknown eligible denominator. Too aggressive on current evidence. |
| Five roots, retaining Map but nesting Buddies                | Protects existing Map habits                 | The fallback if Map users struggle. Keep labels, and place Add where it does not compress the destination targets.                         |

High confidence: keep labels, standardize root headers, prioritize direct time entry, preserve navigation state, and stop automatic feature-driven tab growth. Lower confidence: the exact order of Schedule/Contacts, Map consolidation, Support relocation, and Buddies' eventual long-term placement. No production A/B result is implied.

## Validate before shipping

1. **Prototype the journeys with both established and new users.** Include regular Map users, people who log hours, checkbox-only Publishers, eligible Buddies users, and both platforms. Ask them to log time, record participation, find a Contact on Map, log a Visit, make a Plan with a buddy, export the intended month's Service Report, and find backup/preferences. Observe first selection, wrong turns, extra steps, and recovery. Specifically test leaving Map for Schedule and returning.
2. **Instrument the missing seams within existing privacy and consent rules.** Proposed bounded events: `navigation_destination_selected` (`from`, `to`, `layout_variant`, `reselected`); `contacts_view_changed` (`list` / `map`, source); `quick_action_opened`, `quick_action_selected`, `quick_action_dismissed`; and a bounded entry point carried to the existing creation/report events. Emit visibility/eligibility once per session where needed, not on every render. Record a layout exposure before attributing outcomes. Do not add names, addresses, coordinates, contact identifiers, or recording of screen contents. Document the final contract in `docs/analytics.md` when implementing.
3. **Collect a complete reporting cycle and usable eligible denominators.** Record capability/availability booleans only where needed; do not infer Publisher roles from totals. Verify delivery on released builds. Account for consent, identity resets, native requirements, feature rollout, and version changes. Keep the existing deduplicated screen signal for reach; use a limited experiment/sample for repeated navigation if volume requires it.
4. **Test the risky changes in stages.** First verify labels, root headers, and attribution; then evaluate Map placement and Buddies grouping. Use a stable layout assignment, retain a rollback path, and avoid silently remapping users' places. Do not launch a survey, recruit people, or change PostHog flags as part of this research.
5. **Decide on task outcomes.** Measure correct first destination, successful task completion, steps/time to the intended form, recovery of the chosen Map/date, and reporting/support completion semantics. Do not optimize for session length or tab-tap volume. Protect existing Map task success, logging, monthly report findability, Support outcomes, crashes, and accessibility. Set experiment thresholds and sample size after baseline validation; this dataset does not justify invented precision.

Implementation would also need localized source strings, preservation of role/platform gates and deep links, and updated Help Center guidance for navigation changes. Human-approved translations remain untouched.

## Review scope and deliverables

This work added research artifacts only; it did not change the app, saved dashboards, flags, or campaigns. Industry research used official product announcements, help pages, platform guidance, and inspected first-party screenshots. No logged-in competitor app session was inspected.

Current-app review is source-based. T3 discovered an Android emulator, but its control session was occupied and screenshot/snapshot capture failed. iOS simulator discovery reported an error and returned no iOS device. I did not interrupt another device session. The interactive HTML is an illustrative proposal, not a screenshot or proof of native platform verification.
