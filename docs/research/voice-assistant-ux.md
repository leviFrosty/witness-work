# Voice-first AI input: UX research and recommendation

**Status:** research, 2026-10-21. Nothing here is decided; no ADR yet. Statements about WitnessWork describe the code and docs at the time of writing.
**Question:** how should a "speak your update" feature work in WitnessWork, where the User taps a big mic, talks naturally, watches a glowing orb react to their voice (no live transcript), submits, and then reviews and confirms the actions the AI proposes (add time, plan, add/update Contact, log a Conversation)?

Example utterance used throughout: _"I did two hours this morning with Sarah, and I talked to John at 42 Oak St about the resurrection, follow up next Tuesday."_

## TL;DR

1. **Nobody ships "orb, no transcript, then structured actions" exactly.** ChatGPT, Claude, and Gemini Live all moved _toward_ showing text (an integrated chat view, a scroll-down transcript, a transcript toggle). Todoist Ramble, the closest product, shows no transcript but shows **task cards forming while you speak**. WitnessWork's version works, but only if the **review screen carries the trust that a transcript normally carries**: resolved dates, matched people, and a collapsed "What I heard" row.
2. **Use tap-to-start, tap-to-finish, with an explicit Done button. Never auto-submit on silence.** Every good reference separates "stop recording" from "I'm done talking" badly or not at all, and users get cut off. Voice-activity detection (VAD) is for a gentle nudge ("Tap Done when you're finished"), not for ending the turn.
3. **Explicit review, then a short Undo, not auto-apply.** These entries become service-report data and Contact records. Review once with one primary button (Add all), per-item toggles, tap-to-edit, and forced disambiguation. After Add, an Undo toast is the safety net.
4. **The orb is a level meter with manners.** Fast attack, slow release, idle breathing, a distinct "organizing" state, Reduce Motion fallback, and cheap transforms rather than full-screen shaders on low-end Android. The repo already has a Reanimated waveform with Reduce Motion and level normalization to reuse.
5. **Constraints already in the repo shape the design** (see [§0](#0-what-the-repo-already-decides)): on-device transcription only today (ADR 0018, iOS-only), Scribe AI + sparkles is the AI marker, and the word **"Assistant" is taken** by the rule-based Recommendation engine.
6. **Top pick: Design A, "Orb sheet → Review cards"** ([§8](#8-recommendations-for-witnesswork)). Design C (live cards à la Ramble) is the roadmap if streaming ever fits the privacy model.

Source quality: OpenAI's help center and release notes returned 403 to fetching, so ChatGPT details come from press and third-party guides and are marked as such. Where a search summary and a direct fetch of the same page disagreed, this doc says so.

### Dictation (mic in the composer)

Per a search summary of OpenAI's release notes (the page itself 403'd, so treat as secondary):

- Feb 2025: dictation "shows a text preview of dictated text after recording, shown in a recording bar with a waveform and duration."
- 2026-08-07 (iOS): "if dictation fails because of a connection issue or timeout, ChatGPT automatically retries once."
- The ✕ (discard) / ✓ (finish) pair appears only in a third-party GitHub clone, **not** in anything OpenAI-authored that I could reach. It is nevertheless the dominant mobile pattern (see Wispr below).
- A community report says that after stopping, the mic button disappears and you must send immediately, which one user found worse than recording again. One anecdote, possibly outdated.

Dictation vs voice mode is the useful split: **dictation = you speak, text lands for you to edit, you decide to send**; **voice = conversation**. WitnessWork's feature is dictation-shaped (speak → review → commit) with an orb on top, which is closer to "dictation with an AI step" than to a conversation. That is why it doesn't need interruption, TTS, or full-duplex.

## 3. Speech → structured actions: confirmation patterns

### What the references converge on

- **Show a structured preview, not a transcript.** CRM voice tools and MOCO review structured rows; Ramble shows task cards. A transcript can't be tapped to fix a date.
- **Ambiguity becomes a question, not a guess.** Multiple Johns → ask before writing ([Spotio](https://spotio.com/blog/voice-to-crm/)).
- **Capture literally; don't extrapolate.** Ramble's model is deliberately kept from "over-interpreting" or acting ([Product Talk](https://www.producttalk.org/building-todoist-ramble-how-doist-turned-voice-braindumps-into-real-time-task-capture/)). For WitnessWork this means: say "2 h", never silently turn "this morning" into a 09:00 start time unless the User said it.
- **Correction must be cheap.** Microsoft's HAX library has dedicated patterns for "Support efficient correction" (G9) and "Support efficient dismissal" (G8) ([HAX example library](https://www.microsoft.com/en-us/haxtoolkit/library/example/all/63/99/)); Google's PAIR guidance treats error handling as how trust gets calibrated ([PAIR: Errors + Graceful Failure](https://pair.withgoogle.com/chapter/errors-failing/)). I could not fetch the full text of the 18 HAX guidelines; the 2019 paper has them.
- **Undo beats "Are you sure?" for reversible, frequent actions; confirm only rare, severe ones.** This is practitioner consensus, not controlled research ([DEV Community guide](https://dev.to/137foundry/how-to-choose-between-confirmation-dialogs-undo-windows-and-soft-delete-patterns-1opj): 5-10 s undo windows). Apple-style guidance agrees ([HIG summaries](https://skills.cat/skills/raintree-technology/apple-hig-skills/hig-patterns), secondary).

### Auto-apply + Undo vs explicit confirm

| Approach                                | Fits when                                                            | Why not here                                                                                                                                                                |
| --------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Auto-apply, Undo toast                  | Single, low-stakes, easily reverted (a Todoist task, a timer)        | Time entries feed the monthly service report; a misheard "2" vs "12" or a wrong Contact merge is silent data corruption. Multi-action utterances make a single Undo coarse. |
| **Explicit review, one primary button** | Several writes, mixed risk, ambiguous entities, brand-new AI feature | One extra tap, but it is the trust mechanism, especially with no transcript. **Recommended for v1.**                                                                        |
| Hybrid                                  | Later, once accuracy data exists                                     | Auto-apply only the unambiguous single "Add time" utterance, behind a Settings toggle, with an Undo toast. Measure first (see [§8 analytics](#analytics-and-help-center)).  |

### Recommended review model

For the example utterance, the AI should return these cards (today is Wed 2026-10-21):

1. **Time:** `2 h` · Today, Oct 21 · "this morning" kept as a note, not a start time. Sub-line: "with Sarah" (if Sarah matches a Buddy or Contact, show the match chip).
2. **Contact:** `John` · 42 Oak St · **Pick one:** `John Alvarez (14 Elm St)`, `John Park`, `New contact`. **Add is disabled until picked.**
3. **Conversation (Visit):** Topic "The resurrection" · Today · attached to John.
4. **Follow-up:** `Tue, Oct 27` for John. Always display the **resolved absolute date** next to the spoken phrase ("next Tuesday → Tue, Oct 27") since "next Tuesday" is itself ambiguous in English.

Rules:

- **Group by Contact** so the User sees "John" once with a Visit + Follow-up nested, not three disconnected cards.
- **Per-item checkbox, default on; ambiguous or low-confidence items default off** with an amber "Needs a look" label. A rejected item disappears with Undo; it is not confirmed through a dialog.
- **Tap a card to edit** using the existing Time/Contact/Visit forms prefilled (reuse, don't re-implement). A sheet over a sheet is fine; per the Guardrails, no Cancel button on sheet forms.
- **Highlight inferred fields** (anything not literally spoken: resolved dates, matched Contact) with a small marker, so "literal vs inferred" is visible.
- **Fix by speaking again:** a secondary "Say a change" button appends a short recording ("make it 90 minutes") that re-runs the proposal. Ramble's voice corrections are the model; keep the earlier text in memory for the session so retries never need re-speaking.
- **Follow-up questions** (missing duration, "which day?") appear as a card in the list with 2-4 tappable options, not a spoken question. The feature has no TTS in v1.
- **Multi-action utterances** produce multiple cards; "Add 3" is the one primary action. If nothing was understood: an empty result says so and offers "Try again" and "Add manually" (an empty import already costs nothing in Notes Import; decide the same here).
- After Add: haptic success, sheet closes, toast "Added 3 · Undo" for about 8 s that reverses the whole batch.

## 4. Orb/visualizer design

### What makes it feel responsive

Based on common practice and the existing component; the numbers are starting points to tune on-device, **not** sourced values.

- **Map loudness to a small range.** Scale 1.00 → ~1.25 and glow opacity 0.5 → 1.0. Large excursions look nervous. Normalize to the room and recent peak so quiet speakers still move the orb. `normalizeVoiceLevel` already does this.
- **Fast attack, slow release.** Rise within ~60-80 ms, fall over ~250-350 ms. Interpolate between the ~80 ms meter samples so motion is continuous at 60 fps rather than stepping at 12.5 Hz.
- **Idle breathing even in silence.** ±3% scale on a ~4 s sine, so the User can tell the mic is open when they pause. In the existing waveform, silence shows dots for the same reason.
- **Latency matters more than polish.** Perplexity's reported 1-3 s dead time before the mic is live is the cautionary tale ([futurezone](https://futurezone.at/apps/app-ios-siri-voice-assistant-ai-perplexity-spracheassistent-test-review/403037372)). Show the orb instantly, label it "Getting ready" until audio is flowing, then give a light haptic and bloom. Never let the User talk into a dead mic.
- **Different states must differ in _shape of motion_, not only color** (color-blind users, and glare outdoors):

| State           | Visual                                                                      | Motion character                         | Haptic (light touch, `@/lib/haptics`) | VoiceOver                                  |
| --------------- | --------------------------------------------------------------------------- | ---------------------------------------- | ------------------------------------- | ------------------------------------------ |
| Preparing       | Dim orb, small                                                              | Slow fade-in                             | None                                  | "Getting ready"                            |
| Listening       | Full orb, level-reactive halo                                               | Scale/glow follows voice; idle breathing | `light` on first live audio           | "Listening" (live region, announced once)  |
| Quiet nudge     | Orb steady; Done button pulses; text "Tap Done when you're finished"        | Calm; one slow pulse on Done             | None                                  | Hint on Done                               |
| Organizing      | Orb contracts to a ring with a slow rotating highlight; level input ignored | Continuous, level-independent            | `light` on tap of Done                | "Organizing what you said"                 |
| Review ready    | Orb collapses to a sparkle chip at top; cards appear                        | One-shot spring, then still              | `success` when cards land             | "3 things to review" + focus to first card |
| Error / offline | Orb grey, still; reason line + one action                                   | None                                     | `warning`                             | Error text announced                       |

- **Color:** one accent hue plus its tint from the theme (tokens, not hex). Avoid rainbow gradients and particle/star effects: they read as "magic", which is both off-limits for this community and, per [NN/g](https://www.nngroup.com/articles/ai-sparkles-icon-problem/), part of why AI marking misleads about limits.

### Accessibility

- **Reduce Motion** (iOS) / **Remove animations** (Android): replace the moving orb with a static ring whose _opacity or thickness_ changes with level, no breathing, cross-fades instead of springs. Reduced motion means reducing, not removing, feedback ([summary](https://www.disabilityworld.org/toolkit/glossary/reduced-motion/)). Reanimated's `useReducedMotion`, as in the current waveform, handles detection.
- **WCAG 2.2.2 (Pause, Stop, Hide, Level A)** covers moving content over 5 s; a recording-session visualizer is user-initiated and ends with Done/X, but I have not confirmed from W3C text that this exempts it. The always-present Done/Discard controls are the mitigation.
- **VoiceOver/TalkBack:** one `accessible` element for the orb, with state text, not "image". Announce state _changes_ (once), not levels. The Done and Discard buttons need 48 dp / 44 pt frames and visible text labels (Touch targets in AGENTS.md). Starting the mic while VoiceOver is speaking can swallow the announcement or record it; announce "Listening", then start capture after a short delay, and verify on a device (my judgment, untested).
- **Haptics:** Apple says haptics should have a clear cause and consistent meaning, and not be overused ([HIG: Playing haptics](https://developer.apple.com/design/human-interface-guidelines/playing-haptics.md)). Use at most four: start, Done, results ready, error. **No level-driven continuous haptics.** Respect the app's existing sound/haptics preferences (Audio & Haptics settings); sound cues are off by default for a ministry context (meetings, public places).

### Performance on low-end Android

- Prefer **transform-only animation** (scale/opacity of 2-3 stacked circles driven by a Reanimated shared value on the UI thread) over a full-screen blur or shader. Skia reads shared values with no bridge hop ([Skia + Reanimated](https://www.mintlify.com/shopify/react-native-skia/animations/reanimated), docs summary), and a Skia radial gradient is probably fine, but large-radius blurs and full-screen glows are the usual culprits on cheap GPUs. **Profile on a real low-end device before choosing.**
- Drive the orb from the UI thread; never `setState` per meter sample. The existing waveform follows this with `useFrameCallback` and shared values.
- Stop all animation when the app backgrounds or the sheet isn't focused.

## 6. Discoverability and onboarding

- **Entry points** (owner's two, plus one accelerator):
  1. **Home Quick Actions card:** a large circular mic button with sparkle badge and a rotating example line beneath ("Try: 'Two hours this morning with Sarah'").
  2. **Tab bar "+" menu:** a row "Voice entry" with the sparkle glyph and "Scribe AI" caption, ordered after manual add actions so it doesn't displace muscle memory.
  3. **Accelerator, not sole path:** long-press the "+" to jump straight into listening (TickTick precedent: [help](https://help.ticktick.com/articles/7055782422935240704)). Long-press is invisible, so the menu row must exist.
- **First-run education:** don't add a tour. The first open of the sheet shows (a) the priming card if permission is undetermined, then (b) three tappable-to-copy-free **example chips** that fade through one at a time under the orb: _"I did 2 hours this morning"_, _"Add Maria at 14 Elm St, return visit Thursday"_, _"Plan 90 minutes tomorrow evening"_. They are examples to say, not buttons that submit. After the first successful use, stop showing them automatically and put a "What can I say?" `InfoPopover` beside the title, per the Keep UI simple guardrail.
- **"What can I say" content:** list the four things it can do (add time, plan time, add/update a Contact, log a Conversation), one example each. Also say what it can't do (delete, edit Settings) once, plainly.
- **Placement vs FAB:** the app has a tab bar "+" and a Home card, so a third persistent floating button would add clutter. Not recommended.

## 7. Trust, privacy, and offline

### Identify it as AI, without "magic"

- NN/g found in a 107-person study that **nobody associated the sparkle icon with AI**: associations were save/favorite (16.8%) and visual effects (16.8%). Its guidance is to **pair the icon with a text label** ([NN/g: The AI Sparkles Icon Problem](https://www.nngroup.com/articles/ai-sparkles-icon-problem/)). Sources also tie the icon to a "magic" framing ([Informatics](https://www.informaticsinc.com/blog/november-2024/press-magic-iconography-sparkles-ai-tools), secondary).
- The repo already says AI surfaces use sparkles (`CONTEXT.md`). Recommendation: **keep one small four-point sparkle glyph plus the words "Scribe AI"** on entry points and the review header. No wands, no stardust/particle effects on the orb, no "magic", "poof", or "instantly" copy in any language. If the owner prefers the bolt glyph, the same "glyph + label" rule applies. A bolt reads as speed or power, not AI, so the label does the work either way.
- Don't give it a persona (Copilot's Mico is the counter-example), a name beyond Scribe AI, or a spoken reply voice.

### Privacy copy

Facts to state, in this order and only if true at launch:

1. What leaves the device: with the ADR 0018 design, **only the text** (not audio) is sent to organize it. If the transport changes to audio upload, ADR 0018's reasoning (voice is biometric) needs revisiting first.
2. What's kept: "Nothing is saved until you add it. Your voice isn't saved."
3. Third party: names the zero-data-retention arrangement already used by Notes Import.
4. Contacts' private details: "Names from your Contacts help it hear them correctly; they stay on this device" (true today for Voice Log recognition biasing, ADR 0018; not for the text sent for parsing, which includes whatever names the User spoke).

Evidence caution: a CHI EA 2025 study found users of a purely on-device audio app still described it as "being wiretapped" ([paper](https://pure.skku.edu/en/publications/i-know-my-data-doesnt-leave-my-phone-but-still-feel-like-being-wi/)); the research doesn't show that "not stored" copy alone builds trust. So pair the line with **visible control**: the mic indicator, a ✕ always on screen, a "What I heard" row the User can open to see exactly what was sent, and "Nothing is added until you tap Add".

Where it lives: one line under the orb on first use (the priming card), a link to the Help Center FAQ from the `InfoPopover`, and the footer of the review screen: "Scribe AI can make mistakes. Check these before you add them."

### Offline and unavailable

Show the entry point, **disabled, with a reason**: a small cloud-slash badge on the mic, and tapping it opens an explanation instead of doing nothing.

| Condition                                                                 | Entry point                                                          | On tap                                                                                                        |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Offline                                                                   | Mic at reduced emphasis, "Offline" badge                             | Small sheet: "Voice entry needs an internet connection to organize what you say. [Add time manually] [Close]" |
| Mic permission denied                                                     | Normal                                                               | Priming card: "Open Settings"                                                                                 |
| Went offline _after_ recording                                            | n/a                                                                  | "Couldn't reach Scribe AI. Check your connection." with **Try again** that reuses the captured text           |
| Credits/quota used up (if applicable)                                     | Normal                                                               | Same pattern as Notes Import's Credit explainer                                                               |
| Unsupported (Android until a recognizer exists; unsupported iOS hardware) | **Hidden**, per the AGENTS.md rule for platform-unavailable features | n/a                                                                                                           |

Rationale: temporary conditions (offline) get a visible, disabled entry plus a reason; permanent platform gaps hide it. Wispr likewise refuses to start offline or without permission ([docs](https://docs.wisprflow.ai/articles/5096240724-navigating-the-wispr-flow-app-desktop-ios-and-android)). Because the heavy lifting is server-side, there's no useful offline degradation beyond the manual entry shortcut.

## 8. Recommendations for WitnessWork

### Shared across designs

- **Pipeline:** transcribe on-device (existing module), send text to Scribe AI, return a typed proposal (list of Time / Plan / Contact / Visit / Follow-up actions with `inferred` and `needsChoice` flags), render cards. Same attestation as Notes Import.
- **Naming:** "Voice entry" in the UI; Scribe AI branding on the sheet header; not "Assistant".
- **Copy (English draft, en-US.json only per Guardrails):** title "Voice entry", states "Listening", "Organizing what you said", review header "Here's what I got", primary "Add 3", footer "Scribe AI can make mistakes. Nothing is added until you tap Add."
- **Analytics** (per Guardrails; privacy rules in `docs/analytics.md`): `voice_entry_started` (entry point), `voice_entry_cancelled` (stage, duration bucket), `voice_entry_proposed` (action-type counts, needs-choice count), `voice_entry_resolved` (accepted/rejected/edited counts by type), `voice_entry_failed` (reason: offline, timeout, empty, permission). No transcript or names.
- **Help Center:** a new FAQ entry (how to start, what you can say, what's sent, what to do offline or when it mishears) in `faqs.ts` plus `en-US.json`.

### Design A: Orb sheet → Review cards (recommended)

One large bottom sheet; listening starts as soon as it opens. The orb is the hero, and the same sheet turns into the review list.

**Screen A1. Listening**

- Large detent sheet, themed background. Top row: ✕ (56 pt frame) on the left; sparkle + "Scribe AI" pill centered; `InfoPopover` ("What can I say?") on the right.
- Center: orb ~200 pt, breathing at idle, halo follows voice. "Listening" text, 15 pt, 60% opacity, below it; a small timer appears after 5 s.
- Under the orb: example chips fade through one at a time, only until first successful use.
- Bottom center: 72 pt accent ✓ button labelled "Done". After ~3 s of silence following speech, the button gives one slow pulse and the line "Tap Done when you're finished" fades in.
- Haptics: `light` when audio is live; nothing continuous.

**Screen A2. Organizing**

- Orb contracts to a ring (~96 pt) with a slow rotating highlight; "Organizing what you said…". ✕ becomes "Cancel". Cards appear as skeletons in the lower half after ~400 ms so the next layout is visible.
- Failure: orb greys, one line of reason, "Try again" (reuses the text) and "Add manually".

**Screen A3. Review**

- Orb collapses into the sparkle pill at the top. Header "Here's what I got" and, right, a text button "Say a change".
- Cards grouped by Contact: Time card; John (with the Pick-one chip row); the Visit and Follow-up nested under John. Checkbox default on; low-confidence ones off with "Needs a look". Resolved dates show spoken phrase → absolute date.
- Collapsed row "What I heard" (the transcript lives here, **not** during recording, which honours the owner's no-live-transcript rule while still giving a way to verify).
- Sticky footer: primary **"Add 3"** (disabled with reason until all "Pick one" items are chosen), footer note.
- On Add: `success` haptic, sheet closes, toast "Added 3 · Undo" (about 8 s, undoes the batch).

| Pros                                                                     | Cons                                                                                     |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| Closest to the owner's ChatGPT picture; one sheet carries the whole flow | Review is a second step; fastest "just add 2 h" case still takes 3 taps (mic, Done, Add) |
| Fits the on-device-transcribe → text pipeline and ADR 0018 unchanged     | No feedback that the AI _understood_ until after Done                                    |
| Cheap on low-end Android (transform-only orb)                            | "Say a change" re-run means a second AI call                                             |
| Review screen is also where trust, ambiguity, and editing live           |                                                                                          |

### Design B: Edge glow + docked capsule

The User stays on the current screen. A soft glow runs around the screen edges (Siri's iOS 18.1+ cue) and a compact bottom capsule holds a small pulsing sparkle orb, ✕ and ✓. After Done, proposals slide up as a half-height sheet of the same review cards. Single-action utterances ("2 hours today") auto-apply with an Undo toast; anything with a Contact or Plan goes to review.

| Pros                                          | Cons                                                                                                               |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Feels native and light; no context switch     | Full-screen glow is the costliest thing to render on low-end Android (needs a shader/blur or masked gradient ring) |
| Fast for the common "add time" case           | Two behaviours (auto-apply vs review) make the trust model harder to explain                                       |
| Echoes the system assistant's visual language | Orb is small, so the owner's "big glowing orb" feeling is weaker; Reduce Motion fallback is also less obvious      |

### Design C: Orb + live cards (Ramble-style)

Orb at the top half (~120 pt); as the User speaks, **chips/cards materialize underneath** ("2 h · Today", "John · 42 Oak St", "Follow up · Tue Oct 27"). No transcript, but real-time proof of understanding. Voice corrections ("make that 90 minutes") edit cards live. Done = review in place.

| Pros                                                                                  | Cons                                                                                                           |
| ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Best trust signal and the shortest total time; matches Ramble, the strongest analogue | Needs streaming text or audio to a model during speech: new backend, per-session cost, rate limits, no offline |
| Fixes the "no transcript, can't tell what it heard" problem directly                  | Conflicts with the current ADR 0018 pipeline (final text only) and Credit metering by content hash             |
| Corrections are natural                                                               | Partial-parse flicker and mis-parses on screen mid-sentence; harder to keep calm than a plain orb; more QA     |
| Pairs well with VoiceOver (cards are real elements)                                   | Visually busier than the owner's orb-focused brief                                                             |

### Pick: **Design A**

It is the smallest build that satisfies every stated requirement (orb reacting to voice, no live transcript, explicit submit, AI marker, offline reason, review and confirm), fits the on-device privacy decision already made, and degrades well on cheap Android. Build C's strengths into A cheaply: the skeleton cards in Organizing hint at structure, and "Say a change" gives voice correction without streaming. Revisit C once there is data showing the review step is the main friction.

### Open questions for the owner

1. **Android:** voice capture isn't implemented there (ADR 0018). Is the target an Android on-device recognizer, or a different transport? This gates "both platforms".
2. **Transcript in review:** is a collapsed "What I heard" row acceptable given the no-live-transcript rule? It is the main trust backstop without a transcript; I'd treat it as non-negotiable.
3. **Credits:** does a voice entry draw an Import Credit (voice entry creates records, not history) or is it a separate allowance? Affects copy and offline/quota states.
4. **Auto-apply:** is a future "add time without review" toggle wanted, or should review always stay?
5. **Sparkles vs bolt:** keep sparkle + "Scribe AI" label (repo convention), or bolt? Either way, no wand or particle effects.
6. **Drafts:** if the User goes offline after talking, may the transcribed text be kept in memory only (my proposal), or persisted on-device for a retry later?
