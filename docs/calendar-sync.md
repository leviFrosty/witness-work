# Calendar publishing

Implements the Follow-up portion of [#265](https://github.com/leviFrosty/witness-work/issues/265). Plans and recurring series remain outside this release. The sections below describe iOS; [Android](#android) is a simpler single-device version.

## User behavior

- Calendar Sync is all or nothing. Once a calendar is connected, every upcoming Follow-up is published as a 30-minute event; there is no per-Follow-up choice or duration. Fields an earlier beta saved for that (`calendarIncluded`, `calendarDurationMinutes`) are ignored. Each event's alert mirrors the Follow-up's Notify Me reminder, computed by the same `reminderOccurrences` the app schedules from (including the default reminder time); no Notify Me means no alert. The alert offset (or `none`) is also written into the event URL marker, so a reminder change rewrites the event while alerts a provider adds on its own (Google's per-calendar default notifications) don't cause a rewrite on every check. Alarms are reset to match whenever WitnessWork writes an event. Needs a native build; older binaries ignore the field.
- Onboarding offers a one-tap **Add to Calendar** step on iOS builds with the native module. It reuses the shared or an existing `WitnessWork` calendar, otherwise creates one (iCloud preferred), If another device already publishes, it continues without changes; failures show inline and can be skipped. People who updated past that step get a one-time `calendar_sync` notifications-tray invitation (iOS with the native module) with the same one-tap setup, or **Not Now**. Either onboarding answer, any tray answer or dismissal, connecting, or disconnecting retires it on that device (`promptAnswered` in the device-local calendar store). Skip, **Not Now**, and dismissing also opt the device out (`optedOut`), so a later handoff never turns it on there; skipping after a failed **Add to Calendar** turns off anything it started. A device whose only link to an existing setup is the CloudKit record may still see it until it opens Calendar Sync; tapping it then routes to Settings, which shows the other publisher.
- **Preferences → Calendar Sync** configures a dedicated destination, manual sync, **Turn Off Calendar Sync**, and the primary device. Turning off on the primary asks whether to keep or remove the published events; any other device can only turn off there, and its alert says the events stay. Optional contact names/addresses are shared by all devices (stored in the ownership record), so changing the primary never changes what is published. Notes and topics are not exported. Default calendars and calendars stored only on one device ("On My iPhone") are excluded from the destination picker: another primary could never update them.
- Users create a WitnessWork calendar in a supported account, or explicitly adopt a pre-created dedicated calendar. Google/Outlook setup uses iOS Calendar Accounts; no Google OAuth client or backend integration is required. Accounts that don't allow creating calendars show a dedicated error pointing to existing calendars.
- The **Primary device** list shows devices that have opened Calendar Sync, labeled with the model name when iOS hides the device name, plus when each was last seen. Exactly one may publish; the first device to connect becomes primary automatically. Stale devices can be removed unless they are primary or pending. Calendar controls are available without Supporter; app-data replication retains its existing Supporter requirements, and publishing only waits for an app-data pull when data sync is actually active.
- After a handoff, the new primary reconnects automatically to the calendar with the same title and account, if it already has calendar access. The shared destination replaces stale local connections from earlier publishing; ambiguous matches pause instead of choosing arbitrarily. Otherwise Calendar Sync offers **Reconnect** for that calendar. A device where the user disconnected never reconnects automatically until it is chosen as primary again.
- Local edits publish after a short debounce without an iCloud pull; launch, foreground, and manual sync wait for a complete app-data pull, including the initial iCloud scan, queued reads, and files still downloading. EventKit changes trigger reconciliation while the app is active. Failed maintenance retries after 5, 20, and 60 seconds; further attempts require a data change, foreground, or manual sync. Devices that have never published do no background work. A device that declined or disconnected checks in once more to finish any interrupted batch it owns, then stops (`registered` is cleared). Checks on a device that doesn't publish never report errors or analytics. On non-primary devices, Follow-ups are saved normally and wait for app-data replication and the primary to run; they don't prompt for setup when another device publishes. Calendar publishing requires iCloud sign-in and connectivity even for Google destinations, because ownership must be checked online.
- Disconnect with removal deletes marked events only, including previously exported history. It does not delete the calendar. Disconnect with keep retains the copies. Either choice on the primary stops publishing for all devices; creating a calendar afterwards is allowed. Uninstalling leaves calendar events behind.
- Missing calendars pause publishing. Missing _future_ events also pause: they could still be downloading or have moved to another calendar. Cached EventKit identifiers cannot prove deletion because they can change when events move or an account resyncs. Missing past events are dropped when their Visit is available locally; unknown missing keys still pause until their source data arrives or the user explicitly restores. Users can explicitly **Restore missing events** after checking for moved copies; this may duplicate copies that remain elsewhere. Paused publishing shows in Calendar Sync settings and, only while Calendar Sync is on and this device publishes, as a **Calendar updates paused** notifications-tray item with the fix and **Turn Off**. Failures that need the user (permission, a missing calendar, a changed iCloud account) show at once; connection problems and events still syncing wait until updates have failed for a day (`failingSince`). Dismissing it hides it until updates fail again.
- A Follow-up whose date has passed isn't added to the calendar. A Visit with an invalid date is skipped rather than blocking every other Follow-up.

## Architecture and ownership

`src/app/calendar` projects Visits into calendar entries and orchestrates store/foreground updates. The maintenance fingerprint includes only calendar-relevant fields, so private note/reminder edits do not start publishing. `src/stores/calendarSync.ts` holds the device-local destination and a cache of the shared options, and never enters the iCloud payload. Removals sent to native are limited to published keys, so the payload doesn't grow with Visit history. Contact shares and imports drop the per-Follow-up calendar fields an earlier beta saved.

`modules/calendar-bridge` wraps EventKit directly instead of using the initially proposed `expo-calendar`. The native boundary combines authorization and the EventKit transaction, so no JS code can bypass ownership. No new third-party dependency is needed. The module is retained in Release builds by the existing local-module plugin.

The private CloudKit record `CalendarPublisher/calendar-publishing-v1` holds a JSON String field `state`: registered devices (with last-seen dates), primary, pending primary, busy device, namespace, initial scan date, maximum published horizon, known event keys, original calendar creator, the shared options, and the connected calendar's title and account. Fields added after the first build are optional, so older records decode. Absent shared options default to private details (`includeDetails` false); device-local cached options are not reused. The record's `defaultInclude` field is no longer read or written: every open Follow-up is published. A configuration token invalidates snapshots when destinations or shared options change; native mutations check it against the latest CloudKit state and reject stale snapshots. JavaScript refreshes and rebuilds once before deferring repeated changes. Shared options cannot change during an acquired write, and release checks the acquired account namespace. Updates use CloudKit's `ifServerRecordUnchanged` change-tag comparison; concurrent claims retry against the latest server state. A routine registration/check that changes nothing is not saved, so routine checks don't write the record or race other devices. Device names and opaque IDs are the only identity information stored here; appointment content remains in the selected calendar account.

Every EventKit mutation, including create and cleanup, acquires the durable `busy` field under the current primary. All calls share a native serial executor, including after a JS reload. Switching the primary while idle is immediate. Switching during a write records a pending device and completes on release. Stale/offline former primaries cannot acquire publishing authority. A network failure never falls back to cached ownership.

The busy state does **not** expire. EventKit offers no fencing-token check on a delayed write; expiring the lock would allow an old suspended writer to overlap its replacement. After an interrupted operation, only the owning device can recover it. If that device is permanently lost while busy, automatic transfer remains blocked. This is the availability cost of strict single publishing; the UI tells the user to reopen the previous primary rather than claiming that a timeout makes takeover safe.

A device-only Keychain journal that survives reinstall alongside the device identity records the destination before committing EventKit. A successful write records its keys while releasing ownership (no second calendar scan) and then clears the journal. Recovery after an interruption re-reads committed events and updates the cloud manifest; if the calendar can no longer be read (deleted, permission revoked), recovery keeps the previous manifest and releases anyway, so a handoff can never be blocked by an unreadable calendar. The new primary waits for all previously published event keys to appear in the selected calendar before updating it; cloud ownership transfer alone does not mean calendar-account replication has caught up. Explicit restore is the user-approved escape hatch for genuinely removed events.

Each event URL opens the existing Contact Details route and carries namespace/Visit markers in query parameters. Native IDs are local recovery aids only, cached per calendar so events kept in a previously used calendar are never mistaken for moved events. Reads cover the selected calendar's published date horizon in bounded EventKit query chunks. Reconciliation skips EventKit commit when no event changed, so its own notifications settle after the following check. Mutations operate on marked events only. Switching destinations rebuilds the selected calendar's manifest before projection, so reconnecting a kept calendar can remove its deleted Follow-ups even when publishing previously switched elsewhere. Explicit Visit/Contact deletion, dismissal, and exclusion remove events; contact tombstones also remove owned events when their source Visit is absent, using the contact marker in the event URL. Turning off contact details redacts retained events even if their app records are missing. Missing records in partial app-data sync are never interpreted as deletion. Past appointments are not initially backfilled, but already-exported past events remain maintainable.

## Android

Android publishes from one device with no ownership protocol: no CloudKit record, primary-device list, busy lock, journal, or handoff. Android has no cross-device app-data sync, so there is nothing to coordinate. The user-facing flow matches iOS where it is cheap: the onboarding step and tray invitation (one-tap setup), **Preferences → Calendar Sync** (choose or create a calendar, **Sync now**, **Turn Off Calendar Sync** with keep/remove), all upcoming Follow-ups as 30-minute events, **Include names and addresses**, alerts that mirror Notify Me, the **Calendar updates paused** tray alert, and no backfill of past Follow-ups. The primary-device section, iCloud copy and **Restore missing events** are absent; strings that mention iPhone or iCloud have `…Android` variants. All entry points need a binary with the Android module (`calendarSyncSupported`), so an OTA update can't expose them to older Android builds.

- **Calendars.** The picker lists writable calendars that sync to the device, except each account's primary calendar. Google (and most other providers) ignore calendars created through CalendarContract, so **New calendar** creates a local WitnessWork calendar (`ACCOUNT_TYPE_LOCAL`), reused rather than duplicated if it already exists. To use Google, people create a calendar in Google Calendar and pick it. One-tap setup reuses a single calendar titled WitnessWork, else creates the local one; several matches ask the user to choose.
- **Include names and addresses** lives in the device-local store; there is nothing to share it with.
- **Permissions.** `READ_CALENDAR` and `WRITE_CALENDAR` come from the module's manifest and are requested when the user connects. A denial (or later revocation) pauses publishing with `calendarPermissionErrorAndroid`, an **Open Settings** row that opens the app's system settings, and the paused tray alert. Granting access in the picker clears the error.
- **Maintenance** runs through the same `useCalendarSync` hook: launch, foreground, and a 1.5-second debounce after local edits, with the same retries. There is no app-data pull and no calendar-change listener. After turning off, Android does no background work: there is no interrupted ownership batch to finish.

### Stable event key

Every publish reads the destination's marked events, plans the change in JavaScript (`src/app/calendar/androidEvents.ts`), and applies it in one provider transaction. Events are upserted by Follow-up key, never blindly created, so re-running a publish is always safe.

The key lives in the event **description**, as the link `witnesswork://contact/<contact>/<visit>?followUp=<visit>&alert=<minutes|none>`, the Android counterpart of the iOS event URL. CalendarContract has no app-writable field that also syncs:

- `SYNC_DATA1`–`10` (and `_SYNC_ID`, `DIRTY`) are writable only by sync adapters. Writing as a sync adapter would also mark the event clean, so Google would never upload it.
- `ExtendedProperties` are documented for sync adapters, and nothing documents that Google round-trips them.
- `UID_2445` is app-writable, but Google's sync adapter leaves it null on every event it downloads (a [Pixel probe](https://github.com/williscool/CalendarNotification/pull/276) of 4,761 events found none), so a key there would not reach other devices. A shared iCalendar UID could also make CalDAV servers or Google reject the second device's copy as a UID conflict instead of letting it converge.

Descriptions sync through every provider. So when two Android devices publish into the same Google calendar, each sees the other's events by key. If both created one before syncing, every device keeps the same copy (synced events first, then the lowest `_SYNC_ID`, then the lowest local id) and deletes the rest, so they converge on one event per Follow-up. The marker is visible in calendar apps and may not be tappable there; editing it detaches the event. Changes are detected by parsing the marker, not by comparing the whole description, so text added around it, or a provider turning it into an HTML link, never causes a rewrite on its own; the next real update writes the plain marker back. The alert is part of the marker, as on iOS: reminders are rewritten only when the marker changes, so Google's default notifications don't cause a rewrite on every check. Recurring events and exceptions are never treated as WitnessWork events.

Removal follows iOS: only explicit removals (dismissed or deleted Follow-ups, deleted contacts via the contact id in the marker) delete events, so a device without some Follow-ups (another device's, or partial data from a future sync) never deletes them. Turning off names and addresses redacts every marked event. Unlike iOS, a missing upcoming event is simply recreated: with a single publisher, missing means deleted, not still downloading. Turning off with **Remove Events** deletes marked events in the selected calendar and keeps the calendar.

## Native build and release prerequisites

1. Build a new iOS binary; an OTA update cannot add the native module or calendar permission strings.
2. The iCloud config plugin now enables **CloudKit** alongside **CloudDocuments**. Refresh provisioning for all configured development, beta, and production containers. The calendar purpose string comes from `en-US.json`.
3. TestFlight (Beta) and App Store builds use the **Production** CloudKit environment, which can't create record types on the fly: until the schema is deployed, every ownership call fails and the UI shows the generic connection error. In the development CloudKit environment, exercise registration once to create record type **CalendarPublisher**, with field **state** of type **String**. Deploy that schema to the production environment of each release container (`iCloud.com.leviwilkerson.jwtimebeta` for Beta, `iCloud.com.leviwilkerson.jwtime` for the App Store) before shipping. The Beta container's development schema must be created in CloudKit Console, since no development build uses it. No query indexes are required: the record is fetched by its fixed ID. This PR does not deploy schema or change remote provisioning.
4. Verify on physical devices signed into the same iCloud account: create/adopt iCloud and Google calendars, secondary-account visibility, permission denial/revocation, handoff before calendar replication catches up, app termination during a batch, offline ownership checks, account switching, reinstall, missing/moved events, cleanup, and alert defaults. Simulator compilation and mocked tests cannot certify those behaviors.
5. Only the English locale is changed. The release cut translates the other locales; until then they use the app's English fallback.
6. Android needs a new binary too: the module adds `READ_CALENDAR`/`WRITE_CALENDAR` through its manifest. Calendar events are written on the device and never collected, so the Play Console Data safety answers don't change; confirm that when submitting. Verify a Google calendar on a physical device: the emulator has no signed-in Google account, so Google's handling of the description marker, default notifications and two-device convergence are untested there.

## Checks

`pnpm exec vitest run src/app/calendar` covers projection and orchestration, including rescheduling, removal, privacy, DST, missing data, permission/ownership failures, account changes, failed cleanup, and merge ordering. `androidEvents.test.ts` and `calendarSyncAndroid.test.ts` cover Android's marker, upsert, duplicate convergence, redaction and the connect/disconnect flows against an in-memory provider.

`pnpm run test:calendar-native` compiles and runs the Swift ownership state tests on macOS. They exercise exclusive acquire, pending handoff, stale-owner rejection, crash persistence, no-op registration, device removal, disconnect, legacy record decoding, configuration-token validation, destination manifests, missing-event policy, invalid dates, and contact-marker decoding. These tests do not simulate CloudKit's server or EventKit's database.

Run the standard typecheck, lint, full tests, circular-dependency check, and an iOS simulator build before merging. The research in `calendar-sync-research.md` captures the original recommendation; this document describes the implemented contract and its remaining release validation.
