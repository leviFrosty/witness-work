# PostHog Event Capture Audit Report

## Implementation after the audit

The app now retains **121 of the 254 custom business event types**. The other
133 names and their low-value producers were removed. Static capture sites fell
from 336 in 112 files to 180 in 62 files (including the reserved survey captures). The typed registry in
[`src/lib/analyticsEvents.ts`](src/lib/analyticsEvents.ts) is enforced at capture,
restored-queue loading, and each delivery/retry. Existing anonymous identity
migration and per-route/session screen deduplication remain.

Implemented changes:

- Production-only usage; development, Beta, and unknown configurations retain flags,
  surveys, and diagnostics without ingesting ordinary usage.
- Persisted daily reach caps for foreground activity, onboarding checklist, Supporter
  nudge, and backup reminder impressions. Context separates bounded sources/variants.
- Session caps for timer-start adoption, Buddies entry, push-registration outcomes,
  and iCloud restore probe statuses. Pause/reset timer micro-events are dropped.
- Generic navigation/menu/sidebar, cosmetic preferences, Help Center micro-actions,
  routine background successes, duplicate notification routing, and speculative
  paywall selection events removed. Successful core creation, import/backup outcomes,
  meaningful feature adoption, and important recovery/failure events remain.
- All seven Supporter conversion stages, placement attribution, `gate_flow_id`,
  purchase cancellation/failure, and restore outcomes preserved without daily caps.
- Loaded feature flag readers use SDK exposure metadata and deduplication, with
  a persisted daily flag/variant cap; flag fetching alone is not exposure. Multivariate values have a typed hook.
- Every launch URL removed, including retained events from older anonymous offline
  queues. Legacy identified queues still rotate/drop before startup requests.
- [`docs/analytics.md`](docs/analytics.md) updated with the event budget, current
  journeys, changed denominator semantics, and privacy rules.

Validation: full type checking and lint passed; the complete Vitest suite passed
with 2,320 tests passing and two skipped. An earlier run hit an unrelated
time-dependent redaction assertion that matched `555` inside a timestamp; the
unchanged rerun passed.
The SDK and native-menu regression tests cover both iOS and Android configurations.
These checks do not substitute for post-release ingestion monitoring.

No PostHog dashboard, campaign, billing setting, or ingestion rule was mutated.
A normal app/OTA rollout is still required: old deployed clients continue sending
old events. The replay estimates below are potential event-volume reductions,
not measured post-release savings or a forecast of the bill. Daily impression
caps change chart denominators; version-filtered monitoring and dashboard review
remain rollout work.

## Recommended actions

### 1. Complete rollout of anonymous analytics and the existing capture controls

Current source configures `personProfiles: 'never'` at `src/lib/posthogClient.ts:32`, clears legacy identified state/queued events before startup at `src/lib/anonymousPostHog.ts:25`, deduplicates each screen route per SDK session at `src/lib/analytics.ts:47`, and drops `Application Backgrounded` at `src/lib/posthogClient.ts:51`. Live production remains incompatible with these controls: `$identify`, `$set` and background events were still arriving today, and repeated screens remain common. Verify which store builds and OTA revisions are actually running, then deliver the existing controls to both platforms through the normal release process.

The screen query grouped by identifier, session and route found **122,186 repeat screen events**, **46.7% of screen traffic / 18.5% of all traffic**. Deduplication would retain about 139,245 screen-reach records. Production 1.43.0 accounts for 77,967 repeats out of 163,747 screens; in the latest week, it has 63,169 repeats out of 131,622. Native version alone cannot identify an OTA revision, so these figures establish behavioral mismatch rather than a particular missing release.

The identity query separately confirms **97.20% of 30-day traffic and 98.68% of seven-day traffic have `$is_identified=true`**; this does not infer identification from `person_mode=full` alone. A structural-key-only query found `is_supporter` and `is_donor` in every one of approximately 58,590 `$set` records, supporting legacy supporter/donor person-property updates as their source. Keep needed Supporter status as bounded event context on business events instead of recurring person updates; preserve the repo's anonymous contract.

Anonymous events can be up to four times cheaper, and moving an already identified installation back to anonymous requires a fresh identifier. This checkout already implements that transition. Record the migration boundary because historical identity counts, cohorts and cross-period retention will change; do not promise a fourfold reduction in the actual invoice without checking the account's billing tiers and free allowance. [Anonymous versus identified events](https://posthog.com/docs/data/anonymous-vs-identified-events), [cutting costs](https://posthog.com/docs/product-analytics/cutting-costs).

The existing screen/background/identity controls together address roughly **260,105 events / 39.4%** of this observed window, plus the pricing effect of anonymous events. This is an upper-envelope replay estimate, not savings already achieved or a monthly forecast.

### 2. Block clearly unwanted legacy lifecycle traffic at ingestion, then cap activity

Propose a narrow app-only ingestion rule matching `Application Backgrounded`; it addresses **74,305** observed events and has no explicit saved-artifact dependency. Consider removing `Application Updated` (**3,592**) and RN `$rageclick` (**4,338**) after confirming no current release-health question needs them; touch autocapture is already off in current code at `src/providers/SurveyProvider.tsx:14`. Scope rules to the mobile library and known event names so website traffic, crash reports and surveys are unaffected.

PostHog supports early event filtering with disabled, dry-run and live modes; dropping events before ingestion can reduce usage. A proposed rule can be validated against matching traffic before activation and serve older clients while a release propagates. No rule was activated during this audit. [Event filtering](https://posthog.com/docs/data/event-filtering), [drop events and billing](https://posthog.com/docs/cdp/transformations/drop-events).

For `Application Became Active`, a daily cap is preferable to blindly dropping all activations: a user can return to a still-mounted dashboard without navigating or creating a record. Grouping its 49,890 observed activations by identifier/UTC day retained **15,032** and removed **34,858**, about 70% of that event. Implement a qualified, consent-respecting first activation per chosen day boundary and document its reach semantics; persisted deduplication must survive relaunch and reset correctly with the anonymous identity. `src/lib/posthogClient.ts:33` is the lifecycle configuration seam.

Keep `Application Opened` during the initial reduction because it supports 10 insights across three dashboards. A later daily-open cap could remove about 36,217 additional repeats in the same fixed window, but requires changing session/open-count metrics. Do not apply that cap to a session-frequency question or silently rewrite existing funnels.

The AGENTS.md guardrail explicitly exempts cosmetic changes such as sidebar resizability from analytics. Remove `sidebar_resize_started`, `sidebar_resized`, `sidebar_resize_cancelled`, visibility/view captures, generic tab/context-menu events and routine settings/detail clicks unless a named, temporary experiment requires them. Their current volume is tiny, so this is policy cleanup after the large controls, not the leading bill-saving claim. Evidence: `src/components/ui/SidebarResizeHandle.tsx:29`, `src/components/ui/SidebarToggle.tsx:36`, `src/components/ui/TabBar.tsx:93` and `src/components/ui/menuEntries.ts:65`.

Drop `calendar_published` routine successes at `src/app/calendar/calendarSync.ts:382`: reconciliation runs on launch/foreground/data changes and records success even without a meaningful change (`src/app/calendar/useCalendarSync.ts:113`). Keep connection adoption and bounded failure/recovery. Drop `buddies_push_received` and successful `buddies_push_sync` at `src/app/buddies/BuddiesRuntime.tsx:115`; keep actionable failures and actual sharing/pairing outcomes. Deduplicate unchanged permission-skipped registration at `src/features/buddies/lib/pushRegistration.ts:62`. These maintenance events have zero or low measured traffic, so no present large savings are claimed.

Consolidate backup export's started → file-created → share-requested → exported fanout (`src/features/settings/screens/ImportAndExportScreen.tsx:57`) to attempt, honest terminal outcome and failure. `backup_exported` means the native share call resolved with `outcome: unknown`; it cannot prove a backup was saved. Retire dependent intermediate-stage charts when cutting those events. Likewise preserve timer-start adoption rather than every pause/reset command at `src/features/service-reports/hooks/useStopWatch.ts:79`; a timer command does not prove a Time Entry was saved. [Cutting costs](https://posthog.com/docs/product-analytics/cutting-costs).

### 5. Preserve business funnels and add exposure only where an experiment needs it

Keep the seven stages of the existing [Supporter conversion dashboard](https://us.posthog.com/project/492895/dashboard/2165410): `supporter_feature_gate_viewed` → `supporter_feature_gate_clicked` → `supporter_gate_viewed` → `supporter_gate_clicked` → `paywall_viewed` → `supporter_purchase_started` → `supporter_purchase_completed`. Keep `gate_flow_id` and bounded placement/source attribution: the saved queries correlate stages with them. Only the completion event appears in five saved insights, but cancellations, failures and restore outcomes remain valuable even without a saved chart.

Keep core `time_entry_created`, `contact_created`, `visit_created` and `plan_created`, onboarding start/step/final completion, Notes Import submit/accepted outcomes, backup/import outcomes, recommendation acceptance/undo, mileage adoption/completion and important Supporter-perk enable/recovery outcomes. Generic navigation events should not substitute for real feature adoption. Client purchase completion is not a renewal/refund/revenue ledger; the RevenueCat warehouse source exists but its detailed configuration was inaccessible, so billing-ledger completeness was not established.

There are **no configured experiments**. Six active flags include `notes-import` and `buddies` rollout flags plus four survey targeting flags. The current hook reloads all flags then reads Zustand values at `src/lib/featureFlags.ts:29` and `:44`, without standard SDK exposure access; it also treats only boolean `true` as enabled, so string experiment variants need explicit handling. Standard `$feature_flag_called` is absent from the observed traffic. When starting an A/B test, emit a deduplicated exposure at the actual experience boundary through supported SDK access or the experiment's configured custom exposure event, and retain its conversion/guardrail metrics. Do not emit an exposure on every render, refresh or background flag fetch. Flag request costs are separate from analytics-event volume. [Experiment exposures](https://posthog.com/docs/experiments/exposures), [adding experiment code](https://posthog.com/docs/experiments/adding-experiment-code).

### 6. Fix launch URL privacy and make future event additions accountable

Remove raw lifecycle `url` or reduce it to a bounded launch route. `scrubShareLinkProperties` at `src/lib/shareLinkScrub.ts:9` protects proxy/import payloads, but `witnesswork://contact/<contact.id>/<visit.id>` links are constructed at `src/app/calendar/snapshot.ts:69` and can survive scrubbing; a test at `src/__tests__/shareLinkScrub.test.ts:32` expects a contact URL to remain unchanged. This is a code-level leak path; live private URLs/IDs were not sampled.

For retained events, standardize shared structural fields such as `source` and `entry_mode` across checkbox/form paths of `time_entry_created` (`src/features/service-reports/components/PublisherCheckBoxCard.tsx:81` versus `src/features/service-reports/screens/AddTimeScreen.tsx:250`). Maintain a typed registry of allowed ordinary usage events with a concrete product question, owner, expected trigger frequency and expiry for experiment/launch-only events. Make source outcomes the attribution point rather than capturing both every generic UI action and its domain outcome; update `docs/analytics.md` alongside implementation.

Keep SDK survey/crash contracts outside the ordinary usage allowlist. The opt-in `survey attachment` backup diagnostic is intentional and documented, not ordinary structural analytics; two attachment events were observed, so it is not a present event-count cost driver. No raw contact names, notes, coordinates or imported text were found in ordinary custom event properties. [Capture best practices](https://posthog.com/docs/product-analytics/best-practices).

### Reproducible measurement queries

All operations used `posthog-cli api`; schemas were inspected and event/property presence confirmed with `read-data-schema` before analytics queries. Unknown tools were discovered with `search`, and system table columns were queried from `system.information_schema.columns` before metadata reads. The credential in the project's local `.env` was loaded only into CLI subprocess environments and was never printed or stored in the report. Raw query responses and aggregates were kept in temporary scratch files outside the repository.

The headline inventory query (the precise returned bound above includes fractional seconds):

```sql
-- Noncanonical exploration; governed catalog consulted: no match.
WITH now() AS audit_end
SELECT event,
       count() AS events_30d,
       countIf(timestamp >= audit_end - INTERVAL 7 DAY) AS events_7d,
       uniqExact(distinct_id) AS distinct_identifiers_30d,
       min(timestamp) AS first_seen_in_window,
       max(timestamp) AS last_seen_in_window,
       audit_end - INTERVAL 30 DAY AS window_start,
       audit_end AS window_end
FROM events
WHERE timestamp >= audit_end - INTERVAL 30 DAY AND timestamp < audit_end
GROUP BY event
ORDER BY events_30d DESC
LIMIT 1000
```

Screen-repeat estimate (identifiers stay internal to grouping and are not returned):

```sql
WITH toDateTime('2026-10-04 16:55:28', 'UTC') AS audit_end,
route_sessions AS (
  SELECT distinct_id, $session_id AS session_id,
         properties.$screen_name AS route, count() AS views
  FROM events
  WHERE timestamp >= audit_end - INTERVAL 30 DAY AND timestamp < audit_end
    AND event = '$screen'
  GROUP BY distinct_id, session_id, route
)
SELECT sum(views) AS screen_events,
       count() AS retained_after_dedup,
       sum(views - 1) AS avoidable_repeat_events
FROM route_sessions
```

Daily cap estimate (replace `toDate(timestamp)` with `$session_id` for the session alternative):

```sql
WITH toDateTime('2026-10-04 16:55:28', 'UTC') AS audit_end,
daily AS (
  SELECT event, distinct_id, toDate(timestamp) AS day, count() AS views
  FROM events
  WHERE timestamp >= audit_end - INTERVAL 30 DAY AND timestamp < audit_end
    AND event IN ('supporter_nudge_viewed', 'onboarding_checklist_viewed',
                  'Application Became Active')
  GROUP BY event, distinct_id, day
)
SELECT event, sum(views) AS captured,
       count() AS retained_at_cap, sum(views - 1) AS avoidable_repeats
FROM daily GROUP BY event
```

Identity and environment diagnostic snapshots were read seconds/minutes apart from the inventory. Aggregate `person_mode` together with verified `$is_identified`; do not equate `full` with the identification flag. Structural `$set` key discovery retrieved key names only, never supporter/customer values or private identifiers. Metadata comparison matched whole event-name values inside query/filter JSON, with saved SQL references checked locally; generic All-events queries and external/ad hoc consumers are limitations rather than proof of zero use.

## About this audit

This followed the PostHog `audit-events` workflow with parallel quality and cost checks, adapted to the app's `analytics.capture` wrapper and the required PostHog CLI. Wizard ledger tools were unavailable, so the seven findings were returned directly by reviewers and recorded here; no fake ledger was written. The CLI-required skill refresh was stashed separately and the original tracked skill files restored, leaving this report as the only repository change.

The recommendations are based on source behavior and measured tenant traffic, with saved-artifact dependencies checked before proposing removal. No release, capture-policy change, tenant mutation or dashboard rewrite was performed. The next implementation should deliver existing controls first, apply selected bounded captures, retire obsolete charts/documentation, verify both platforms, and compare event rate plus identified share after deployment.
