# Calendar publishing

Implements the Follow-up portion of [#265](https://github.com/leviFrosty/witness-work/issues/265). Plans and recurring series remain outside this release.

## User behavior

- A Follow-up's **Show in Calendar** choice and duration are saved with its Visit and travel through existing app-data sync. Existing Follow-ups are not opted in automatically. Reminders remain independent.
- **Preferences → Calendar Sync** configures a dedicated destination, manual sync, disconnect with keep/remove choices, and the primary device. Default inclusion for new Follow-ups and optional contact names/addresses are shared by all devices (stored in the ownership record), so changing the primary never changes what is published. Notes and topics are not exported. Default calendars and calendars stored only on one device ("On My iPhone") are excluded from the destination picker: another primary could never update them.
- Users create a WitnessWork calendar in a supported account, or explicitly adopt a pre-created dedicated calendar. Google/Outlook setup uses iOS Calendar Accounts; no Google OAuth client or backend integration is required. Accounts that don't allow creating calendars show a dedicated error pointing to existing calendars.
- The **Primary device** list shows devices that have opened Calendar Sync, labeled with the model name when iOS hides the device name, plus when each was last seen. Exactly one may publish; the first device to connect becomes primary automatically. Stale devices can be removed unless they are primary or pending. Calendar controls are available without Supporter; app-data replication retains its existing Supporter requirements, and publishing only waits for an app-data pull when data sync is actually active.
- After a handoff, the new primary reconnects automatically to the calendar with the same title and account, if it already has calendar access. Otherwise Calendar Sync offers **Reconnect** for that calendar. A device where the user disconnected never reconnects automatically until it is chosen as primary again.
- Local edits publish after a short debounce without an iCloud pull; launch, foreground, and manual sync pull app data first. Devices that have never published do no background work. On non-primary devices, Follow-ups are saved normally and wait for app-data replication and the primary to run; they don't prompt for setup when another device publishes. Calendar publishing requires iCloud sign-in and connectivity even for Google destinations, because ownership must be checked online.
- Disconnect with removal deletes marked events only, including previously exported history. It does not delete the calendar. Disconnect with keep retains the copies. Either choice on the primary stops publishing for all devices; creating a calendar afterwards is allowed. Uninstalling leaves calendar events behind.
- Missing calendars pause publishing. Missing _future_ events published by another device also pause: they could still be downloading after a device handoff or have moved to another calendar. Events this device had already seen in the calendar (deleted in a calendar app) are recreated, and missing past events are dropped from the manifest, so routine clean-up doesn't stop publishing. Users can explicitly **Restore missing events** after checking for moved copies; this may duplicate copies that remain elsewhere. Paused publishing shows on the Follow-up form, not only in Settings.
- A Follow-up whose date has passed isn't added to the calendar; the form says so. A Visit with an invalid date or duration is skipped rather than blocking every other Follow-up.

## Architecture and ownership

`src/app/calendar` projects Visits into calendar entries and orchestrates store/foreground updates. `src/stores/calendarSync.ts` holds the device-local destination and a cache of the shared options, and never enters the iCloud payload. Removals sent to native are limited to published keys, so the payload doesn't grow with Visit history. Contact shares strip calendar consent, including on import.

`modules/calendar-bridge` wraps EventKit directly instead of using the initially proposed `expo-calendar`. The native boundary combines authorization and the EventKit transaction, so no JS code can bypass ownership. No new third-party dependency is needed. The module is retained in Release builds by the existing local-module plugin.

The private CloudKit record `CalendarPublisher/calendar-publishing-v1` holds a JSON String field `state`: registered devices (with last-seen dates), primary, pending primary, busy device, namespace, initial scan date, maximum published horizon, known event keys, original calendar creator, the shared options, and the connected calendar's title and account. Fields added after the first build are optional, so older records decode. Updates use CloudKit's `ifServerRecordUnchanged` change-tag comparison; concurrent claims retry against the latest server state. An update that changes nothing is not saved, so routine checks don't write the record or race other devices. Device names and opaque IDs are the only identity information stored here; appointment content remains in the selected calendar account.

Every EventKit mutation, including create and cleanup, acquires the durable `busy` field under the current primary. All calls share a native serial executor, including after a JS reload. Switching the primary while idle is immediate. Switching during a write records a pending device and completes on release. Stale/offline former primaries cannot acquire publishing authority. A network failure never falls back to cached ownership.

The busy state does **not** expire. EventKit offers no fencing-token check on a delayed write; expiring the lock would allow an old suspended writer to overlap its replacement. After an interrupted operation, only the owning device can recover it. If that device is permanently lost while busy, automatic transfer remains blocked. This is the availability cost of strict single publishing; the UI tells the user to reopen the previous primary rather than claiming that a timeout makes takeover safe.

A device-only Keychain journal that survives reinstall alongside the device identity records the destination before committing EventKit. A successful write records its keys while releasing ownership (no second calendar scan) and then clears the journal. Recovery after an interruption re-reads committed events and updates the cloud manifest; if the calendar can no longer be read (deleted, permission revoked), recovery keeps the previous manifest and releases anyway, so a handoff can never be blocked by an unreadable calendar. The new primary waits for all previously published event keys to appear in the selected calendar before updating it; cloud ownership transfer alone does not mean calendar-account replication has caught up. Explicit restore is the user-approved escape hatch for genuinely removed events.

Each event URL opens the existing Contact Details route and carries namespace/Visit markers in query parameters. Native IDs are local recovery aids only, cached per calendar so events kept in a previously used calendar are never mistaken for moved events. Reads cover the selected calendar's published date horizon in bounded EventKit query chunks. Mutations operate on marked events only. Explicit Visit/Contact deletion, dismissal, and exclusion remove events; missing records in partial app-data sync are never interpreted as deletion. Past appointments are not initially backfilled, but already-exported past events remain maintainable.

## Native build and release prerequisites

1. Build a new iOS binary; an OTA update cannot add the native module or calendar permission strings.
2. The iCloud config plugin now enables **CloudKit** alongside **CloudDocuments**. Refresh provisioning for both configured dev/prod containers. The calendar purpose string comes from `en-US.json`.
3. In the development CloudKit environment, exercise registration once to create record type **CalendarPublisher**, with field **state** of type **String**. Deploy that schema to the production environment of each release container before shipping. No query indexes are required: the record is fetched by its fixed ID. This PR does not deploy schema or change remote provisioning.
4. Verify on physical devices signed into the same iCloud account: create/adopt iCloud and Google calendars, secondary-account visibility, permission denial/revocation, handoff before calendar replication catches up, app termination during a batch, offline ownership checks, account switching, reinstall, missing/moved events, cleanup, and alert defaults. Simulator compilation and mocked tests cannot certify those behaviors.
5. Only the English locale is changed. Obtain human-approved translations before release; other locales retain the app's existing English fallback.

## Checks

`pnpm exec vitest run src/app/calendar` covers projection and orchestration, including rescheduling, removal, privacy, DST, missing data, permission/ownership failures, account changes, failed cleanup, and merge ordering.

`pnpm run test:calendar-native` compiles and runs the Swift ownership state tests on macOS. They exercise exclusive acquire, pending handoff, stale-owner rejection, crash persistence, device registration without redundant writes, device removal, disconnect, and decoding records from the first build. These tests do not simulate CloudKit's server or EventKit's database.

Run the standard typecheck, lint, full tests, circular-dependency check, and an iOS simulator build before merging. The research in `calendar-sync-research.md` captures the original recommendation; this document describes the implemented contract and its remaining release validation.
